[프로젝트] V2X 차량용 범용 HTTPS 통신 데몬 개발 및 기술 자문

1. 프로젝트 개요

  • 프로젝트명: v2x-httpsd (Vehicle-to-Everything HTTP Secure Daemon for PKI Client)
  • 개발 기간: 2025.03 ~ 2025.06
  • 목표: 완성차 기업(OEM)별 상이한 통신 데몬으로 인한 개발 지연 문제 해결. OEM이 자체 데몬을 제공하기 전까지 내부 공정 계획을 미리 진행할 수 있도록, 여러 OEM(JLR, BMW) 및 Third-Party PKI Client를 지원하는 범용 테스트 데몬 개발
  • 참여 역할: 아키텍처 설계 및 코드 구현 총괄 (1인 개발), LG전자 V2X Manager팀 및 베트남 지사 개발팀 대상 기술 자문

2. 수행 역할 및 상세 활동

가. S/W 아키텍처 설계 및 구현
  • 초기 전략 수립: 과거 프로젝트(ASN.1 자동화 툴)의 지연 경험을 바탕으로, 초기 3주는 C언어 스타일로 핵심 기능(PCL-libcurl 연동)의 프로토타입을 신속하게 구현하는 전략을 채택했습니다. 이를 통해 v2x-httpsd의 완성도와 무관하게 V2X Manager와의 연동 테스트 등 고객사의 공정 계획이 선행될 수 있도록 지원했습니다. 기능 동작 검증 후, 약 1개월 시점부터 객체지향 및 Spring 프레임워크 설계 철학을 적용하여 코드를 리팩토링했습니다.
  • 확장성을 고려한 아키텍처 설계:
    • OCP(개방-폐쇄 원칙) 적용: 신규 Third-Party PKI Client SDK 추가 시, 기존 코드 수정 없이 기능 확장이 가능하도록 C++ 템플릿 특수화(Template Specialization)를 적용하여 아키텍처를 설계했습니다.
    • SRP(단일 책임 원칙) 적용: CurlWrapper, HTTP_Url, Adapter 등 각 클래스의 책임을 명확히 분리하여 설계했습니다. 이를 통해 통신 관련 이슈 발생 시 트러블슈팅 시간을 기존 1일 이상에서 30분 이내로 단축하는 성과를 달성했습니다.
    • 템플릿 메소드 패턴 적용: IPC 종류(PCL, Posix Queue 등)와 무관하게 공통 직렬화/역직렬화 로직을 공유하도록 IPC_API 추상 인터페이스를 설계하여, JLR(PCL)과 BMW(Posix Queue)의 상이한 요구사항을 단일 아키텍처 내에서 수용했습니다.
  • IPC 라이브러리(PCL) 한계 극복:
    • PCL 라이브러리 read 함수의 비직관적 동작 방식(원하는 토픽을 지정할 수 없는 문제)을 해결하기 위해 생산자-소비자(Producer-Consumer) 패턴을 적용한 Pcl_ReceivedQueueMonitor 클래스를 설계했습니다.
    • 백그라운드 스레드가 모든 토픽을 수신하여 내부 큐에 분류하고, 사용자는 일반적인 동기식 I/O처럼 원하는 토픽의 데이터만 읽을 수 있도록 API 동작 방식을 개선했습니다.
  • 안정성 확보를 위한 저수준(Low-level) 시스템 분석 및 적용:
    • C++ 예외(Exception) 미처리 시 RAII 기반의 자원 해제가 실패하는 문제를 방지하기 위해, 리눅스 커널의 프로세스 종료 메커니즘(do_exit, SIGABRT 등)을 분석했습니다.
    • 커널 동작 분석 결과를 바탕으로, 프로세스 비정상 종료 시에도 등록된 정리 함수가 호출되도록 안정적인 종료(Graceful Termination) 처리 로직을 구현하여 시스템 안정성을 확보했습니다.
    • 임베디드 환경의 메모리 안정성을 위해 RAII, 스마트 포인터 등 C++ Core Guideline을 준수하여 개발했습니다.
나. 글로벌 기술 자문 및 협업 (베트남 개발팀 대상)
  • 기술적 방향성 제시 및 설득: 프로젝트 초기, 특정 SDK에 종속적인 API 설계에 대한 동료의 우려("It makes the code depends on CMS")에 대해, 향후 다른 SDK 확장까지 고려한 객체지향 설계의 기술적 타당성(OCP, SRP)을 근거로 제시하며 설득했습니다.
  • 선제적인 문제 진단 및 해결책 제공:
    • 시간 동기화 문제 해결: 과거 BMW 프로젝트 경험을 바탕으로, 동료가 겪던 원인 불명의 SSL 통신 오류의 근본 원인이 '디바이스 시간 불일치'임을 로그("The log says your device time is not correct")를 통해 진단했습니다. 문제 재발을 막기 위해 시스템의 UTC 시간을 확인하는 -u 옵션을 v2x-httpsd에 추가 개발하여 제공했습니다.
    • 타사 SDK 버그 분석: 인증서 발급 실패의 원인이 타사 SDK(CMS PKI Client)의 버그에 있음을 분석했습니다. 요청 데이터 크기가 566바이트여야 함에도 144바이트만 전송되는 문제를 특정하여 원인을 규명했습니다.
    • 서버 환경 문제 해결: 테스트 실패 원인이 서버 측 API 토큰 사용 횟수 제한(30회)임을 파악하고, 관리자에게 요청하여 사용 한도를 100회로 증설하여 안정적인 테스트 환경을 구축했습니다.
  • 원격 협업 효율화를 위한 기술 지원:
    • 빌드 환경 지원: Yocto 빌드에 실패하는 동료에게 정확한 빌드 레시피(.bb 파일)를 제공했습니다.
    • 테스트 환경 지원: 테스트 서버에 로그인하지 못하는 동료를 위해 직접 계정 비밀번호 초기화를 지원했습니다.
    • 기술 문서 제공: 원활한 테스트와 시스템 이해를 돕기 위해 테스트 가이드 및 시스템 시퀀스 다이어그램을 직접 작성하여 공유했습니다.

3. 결과 및 성과

  • 핵심 목표 달성: 다수의 기술적 난관을 해결하고, 최종적으로 V2X 차량에 보안 인증서가 성공적으로 저장되는 프로젝트의 핵심 목표를 달성했습니다.
  • 고객사 요구사항 100% 충족: JLR(PCL), BMW(Posix Queue)의 상이한 IPC 요구사항을 모두 충족하는 유연한 구조를 완성했으며, 사설 SSL/TLS 인증서 지원 및 JSON ZIP 변환 기능 등 모든 요구사항을 구현했습니다.
  • 프로세스 효율화: 단일 책임 원칙(SRP) 기반 설계를 통해, 원인 파악에 1일 이상 소요되던 통신 관련 이슈의 트러블슈팅 시간을 30분 이내로 단축했습니다.

4. 적용 기술

  • Language: C++17
  • Core Concepts: OOP, SOLID Principles (OCP, SRP), Design Patterns (Template Method, Producer-Consumer)
  • Libraries & Tools: libcurl, PCL, POSIX IPC (Queue, Socket), Yocto Project, Git, CMake
  • Knowledge: Linux Kernel (Process Termination), Network (HTTP/TLS)
